LeetCode Round Curriculum

The full map for the algorithms & data-structures loop — data structures first, then algorithm basics, then the interview pattern playbook, up to the timed mock itself. The midday lesson walks this map node by node; each lesson links back here, and each node below links forward to its lesson as it's written. Companion to the AI/ML round map.

Phase 0 — Data structures: the basics

The vocabulary of every coding interview. Know how each structure is built and what each operation costs — everything else is composition.

L1 · Arrays: the foundation Planned

Contiguous memory, O(1) indexing by arithmetic, static vs dynamic arrays; why append is usually cheap and insert-at-front is not. Answers "why is indexing O(1)?"

L2 · Strings: the array's tricky sibling Planned

Immutability in Python, encoding in one paragraph, the O(n) operations people forget (concatenation in a loop), and why strings love two pointers. Answers "why is s += ch in a loop O(n²)?"

L3 · Linked lists: pointer surgery Done

Nodes and links; reversal (iterative and recursive), dummy heads, merging two lists — rearranging pointers without losing the list. Answers "reverse a linked list."

L4 · Stacks & queues: LIFO, FIFO, and the deque Planned

The two auxiliary structures behind nesting problems, BFS, and sliding windows; Python's deque, and why list.pop(0) is a trap. Answers "implement a queue using stacks."

L5 · Hash maps & sets: the O(1) workhorse Planned

Average O(1) lookup/insert — and what "average" hides: hashing, collisions, load factor, hashability. Answers "two sum."

L6 · Frequency & grouping patterns Planned

Counter-driven thinking: anagrams, top-k frequent elements, first unique character. Answers "group anagrams."

Phase 1 — Algorithms: the basics

How to reason about cost and correctness. With data structures under your belt, complexity finally has something concrete to bite on.

L7 · Big-O, Ω, Θ: what complexity actually measures Done

What O(n) actually promises — and what it doesn't. Drop the constants, keep the growth; worst case is the default language of interviews. Answers "what's the complexity of your solution?"

L8 · Recursion: the call stack as a tool Planned

Base case, trust the recursion, combine. The call stack as scratch space; depth limits and why iteration sometimes wins. Answers "why is your recursion correct?"

L9 · Sorting: why O(n log n), and what Python actually runs Planned

Merge sort and quicksort as divide-and-conquer templates; the comparison-sort lower bound in one paragraph; Timsort, stability, and key functions. Answers "sort this in O(n log n)."

L10 · Amortized analysis & complexity pitfalls Planned

Why appending to a list is O(1) even though resize is O(n) — now motivated by the dynamic arrays from L1. The accounting method in one lesson; the traps (hidden O(n) inside loops, string concatenation). Answers "isn't that O(n²)?"

L11 · Python for interviews: the working toolkit Planned

The 20% of the language behind 80% of solutions: lists, dicts, sets, heapq, deque, bisect, defaultdict/Counter, itertools — and the cost of each operation, cold. Answers "why is Python fine for interviews?"

L12 · Constraint decoding: let n choose your algorithm Planned

n ≤ 10 → exponential may pass; n ≤ 10⁵ → O(n log n); n ≤ 10⁹ → O(log n) or O(1). Read the constraints as the intended solution before you write a line. Answers "how do you pick an approach?"

Phase 2 — Interview techniques: the pattern playbook

The moves interviewers expect you to know cold. Each one turns a whole problem family into a template.

L13 · Two pointers Planned

Opposite ends, same direction, fast/slow — the first pattern to reach for on sorted arrays and linked lists. Answers "find a pair summing to k."

L14 · Sliding window Planned

Fixed and variable windows; when to expand vs shrink. The template behind most substring problems. Answers "longest substring without repeating characters."

L15 · Fast & slow pointers: Floyd's cycle detection Planned

Why the meeting-point math works, and the second phase that finds the cycle start. O(1) space elegance on the linked lists from L3. Answers "detect a cycle."

L16 · Prefix sums & difference arrays Planned

Trade O(n) space for O(1) range queries; difference arrays for range updates. Answers "sum over subarrays, fast."

L17 · Subarray patterns: Kadane and beyond Planned

Maximum subarray as the canonical "extend or restart" decision; generalizes to circular and product variants. Answers "maximum subarray."

L18 · Binary search: the template Planned

Lower/upper bound thinking: search the predicate, not the value. The lo/hi invariant that ends off-by-one errors forever — plus rotated arrays and staircase search in sorted matrices. Answers "search in a rotated array."

L19 · Binary search on answer Planned

When the answer space is monotonic, binary-search it: capacities, speeds, days. The most under-taught binary search pattern. Answers "minimum eating speed."

L20 · Monotonic stacks & deque patterns Planned

Next-greater-element template; deque for sliding-window maximum. The stacks from L4, weaponized. Answers "daily temperatures."

L21 · Intervals: merge, insert, meeting rooms Planned

Sort by start, then one pass. The template behind scheduling problems everywhere. Answers "merge intervals."

L22 · Greedy: when it works, how to argue it Planned

When local optimality is safe: the exchange argument in one paragraph. Learn the smell of a greedy problem — and when to distrust it. Answers "why is greedy correct here?"

L23 · Design: LRU cache Planned

Hash map + doubly linked list = O(1) get/put with eviction — L3 and L5 composed. The design problem every loop asks. Answers "design an LRU cache."

Phase 3 — Trees & heaps

If you can traverse it, you can solve it. Trees are recursion made visible.

L24 · Traversals: recursive and iterative Planned

Preorder/inorder/postorder by recursion — then with an explicit stack. Simulating the stack is the skill that transfers everywhere. Answers "traverse without recursion."

L25 · BSTs: properties, validation, search Planned

The invariant (left < node < right) does all the work: search, insert, validate in O(h). Answers "validate a binary search tree."

L26 · LCA, diameter, path sums Planned

One-pass post-order patterns: return info upward, track the answer globally. Answers "lowest common ancestor."

L27 · Serialization & building trees Planned

Encode a tree to a string and back (preorder + nulls); build from traversal pairs. Tests whether you really understand structure. Answers "serialize a binary tree."

L28 · Top-k patterns Planned

A heap of size k beats a full sort: O(n log k). The min-heap/max-heap decision rule, cold. Answers "kth largest element."

L29 · Two heaps: running median Planned

Max-heap + min-heap with a balancing invariant — order statistics on a stream. Answers "find the median from a data stream."

L30 · Merge k sorted lists Planned

Push heads into a heap, pop-min repeatedly: O(N log k). Heaps as the merger of sorted streams. Answers "merge k sorted lists."

L31 · Tries Planned

Prefix trees: build once, query in O(m). Autocomplete, word search, prefix scores. Answers "implement a trie."

Phase 4 — Graphs

Nodes and edges are everywhere once you see them — grids, schedules, networks.

L32 · BFS/DFS: traversal & components Planned

Traversal as the foundation: connected components, flood fill, grids as graphs. Iterative DFS to dodge recursion limits. Answers "number of islands."

L33 · Topological sort Planned

Kahn's algorithm (indegrees) and DFS finish-order for DAG ordering; cycle detection falls out for free. Answers "course schedule."

L34 · Union-find Planned

Path compression + union by rank ≈ O(α(n)). Dynamic connectivity without ever building the graph. Answers "are these nodes connected?"

L35 · Shortest paths: Dijkstra & BFS Planned

BFS for unweighted, Dijkstra for weighted (why the heap works), Bellman-Ford when negatives lurk. Answers "shortest path in a grid."

Phase 5 — Dynamic programming

The boss level. Recurrence first, table second, always.

L36 · 1D DP: recurrence thinking Planned

Define dp[i] in terms of smaller subproblems: climbing stairs, house robber. The state definition IS the solution. Answers "how do you define the state?"

L37 · 2D grid DP Planned

Unique paths, min path sum: the grid as a DAG. Space optimization down to one row. Answers "minimum path sum."

L38 · Knapsack family Planned

0/1 vs unbounded: the loop order is the entire difference. Subset sum as the gateway drug. Answers "partition equal subset sum."

L39 · LIS & patience sorting Planned

O(n²) DP first, then the O(n log n) patience-sorting upgrade — and why the piles work. Answers "longest increasing subsequence."

L40 · Interval & palindrome DP Planned

Expand-around-center vs the DP table; interval thinking for burst-balloon-style problems. Answers "longest palindromic substring."

L41 · State-machine DP: stocks Planned

States as nodes, transitions as edges — cooldowns, fees, k transactions. The most transferable DP mental model there is. Answers "best time to buy and sell stock."

Phase 6 — Bits & string matching

Two small toolkits with outsized leverage.

L42 · Bit manipulation essentials Planned

XOR tricks, bit masks, Kernighan's bit count. A small toolkit with outsized cleverness. Answers "single number."

L43 · String matching: know KMP exists Planned

Naive vs KMP vs Rabin-Karp at the idea level. In Python, in is fine — know why. Answers "implement strStr()."

Phase 7 — The round itself

The round is a performance, not an exam. Train the performance.

L44 · Pattern recognition drills Planned

Given a problem statement, name the pattern in 60 seconds. Speed of classification is the real interview skill — the code follows.

L45 · Timed mocks: 2 problems, 45 minutes Planned

Talk while you code, narrate tradeoffs, manage the clock. The full performance, rehearsed until it's boring.

L46 · Follow-ups & optimization under pressure Planned

"Now do it in O(1) space." Thinking aloud through the second solution is where offers are won and lost.

L47 · Debugging on the clock Planned

Dry runs, invariants, and the 2-minute bug hunt. Never stare at code — trace it.
