Hash Maps & Sets: The O(1) Workhorse

Lesson L5 · the card catalog — every name has a slot, but two names can land on the same one

Algorithms and data structures Lesson

Builds on

L1 (Arrays: The Foundation) — a[i] is O(1) because the address is computed, never searched (base + i × wordsize). The hash map keeps that contract and generalizes the key: slot = hash(key) mod m is still arithmetic, still O(1).

L2 (Strings) — strings are the canonical keys, and the hashability contract explains why str and tuple hash but list does not: a key's hash must not change while it lives in the table, so keys must be immutable.

L7 (Big-O) — today's vocabulary cashes in the average vs. worst case distinction: hash maps are O(1) expected, Θ(n) adversarial. Say which one you mean.

The intuition: a card catalog made of wood

You walk in with a title — the librarian does not scan every drawer. She knows a rule (the hash function) that turns any title into a drawer number, walks straight to it, and opens it. That's the whole data structure: a rule that converts names into slot numbers, plus a plan for when two names pick the same slot.

A hash function takes any key and returns an integer. Three requirements: deterministic (same key, same hash — always), fast, and uniform (keys spread evenly across slots). The contract is one-directional: equal keys → equal hashes. Unequal keys may share a hash — that's a collision, and it's arithmetic, not a bug.

The math: collisions arrive early

This is the birthday bound, and it's worth deriving once. The probability that n random keys land in n distinct slots of m:

P(no collision) = (1 − 1/m)(1 − 2/m)…(1 − (n−1)/m) ≈ e−n²/2m

Set that to 1/2 and solve: n ≈ √(2m ln 2) ≈ 1.18√m. With 100 slots, ~12 random keys give even odds of a collision. Collisions aren't edge cases — they're the normal weather, and the table is engineered around them.

The mechanism: chaining, probing, and what Python actually does

Two classical answers. Separate chaining: each slot holds a linked list; colliding keys line up. Open addressing: no lists — if the slot is taken, probe for the next free one (linear probing walks +1, +2, …; quadratic and double hashing probe in smarter strides).

CPython's dict is open addressing with a twist: the table size is always a power of two, so the slot is hash(key) & (m−1) — a bitmask instead of a modulo — and collisions are resolved by a perturbation probe sequence that pseudo-randomizes the walk. It caches each key's hash in the table, so lookups never re-hash. And it keeps the load factor α = n/m at or below 2/3: more than two-thirds full, and it doubles. A set is the same table with no values — keys only, a membership oracle.

The math that matters: why "expected O(1)" is honest

Assume simple uniform hashing: every key lands on every slot with equal probability. With load factor α = n/m, a lookup walks on average 1 + α probes — the slot itself plus the chain behind it. CPython doubles at α = 2/3, so lookups cost ~1.7 probes on average, forever, no matter how large n grows. That's what "O(1) average" means: the cost is bounded by a constant because α is bounded by a constant.

Inserts stay cheap for the same reason appends did in L1: doubling. Resizing an n-element table costs O(n), but it happens only at sizes 1, 2, 4, 8, … — the same Σ2k ≈ 2n argument from L1, so inserts are amortized O(1). Three corollaries for the round:

  1. Worst case is still Θ(n) if an adversary feeds colliding keys — which is why Python randomizes string hashing (SipHash, per-process seed) after the hash-flooding DoS attacks of 2011–12.
  2. Hashing a string costs O(length of the key) — the "O(1)" hides a linear scan of the key.
  3. Never persist a hash across runs — PYTHONHASHSEED randomization means hash("ana") differs every process.

The canonical problem: Two Sum (LeetCode 1)

"Given an array of integers nums and an integer target, return indices of the two numbers that add up to target." Brute force checks every pair — n(n−1)/2 of them, Θ(n²). The hash-map insight is a question, not a loop: for each element x, what partner am I looking for? The answer is target − x — and a hash map answers "have I seen it?" in O(1):

def twoSum(nums: list[int], target: int) -> list[int]:
    # seen[value] = index. One pass: for each x, ask the map
    # "have you seen target - x?" before remembering x. LC 1.
    seen: dict[int, int] = {}
    for i, x in enumerate(nums):
        need = target - x
        if need in seen:                    # complement found
            return [seen[need], i]
        seen[x] = i                         # remember x for later elements
    raise ValueError("no solution")

Complexity: n iterations × O(1) average map ops → O(n) time; the map holds at most n entries → O(n) space. On [2,7,11,15], target 9: i=0, need 7 — not in {}, remember {2:0}; i=1, need 2 — in the map → return [0,1].

How to spot it: the tells

  • "have I seen this before?" / "first duplicate" → set: membership in O(1).
  • "for each element, find its partner/complement" — pair summing to target, anagram twin → dict, Two Sum's shape.
  • "count / most frequent / group by" → dict as counter (L6 turns this into a whole lesson).
  • membership tests inside a loop → build a set once: n × O(n) becomes n × O(1). This lesson's hidden-cost trap.

The pitfalls

  1. Unhashable keys — d[[1,2]] = x → TypeError: unhashable type: 'list'. Use tuple or frozenset; a mutable key could change its hash mid-life and get lost in the wrong slot.
  2. Mutating during iteration → RuntimeError: dictionary changed size during iteration. Iterate over list(d) if you must mutate.
  3. d[k] vs d.get(k) — brackets raise KeyError on a miss; .get(k) returns None or your default.
  4. in on a list is a scan — O(n), not O(1). Put candidates in a set first.
  5. Sets are unordered; dicts are insertion-ordered (since 3.7). Never depend on set order — it's randomized per run.
  6. The hash isn't free — hashing a 10KB string key costs a 10KB scan.

🎯 Your 30-second interview answer

"An array gives O(1) by integer index — pointer arithmetic, no scanning. A hash map generalizes it: slot equals hash of the key mod capacity, so lookup by name costs the same. The catch is collisions — the birthday bound says they arrive after about root-m keys, so the table chains or probes and keeps the load factor bounded by doubling on resize. Under uniform hashing the expected probe count is one plus alpha, a constant, so operations are O(1) average — the doubling argument is the same one that made appends amortized O(1) back in L1. The interview reflex: whenever the problem asks 'have I seen its partner?' — Two Sum is the canonical shape: one pass, look up the complement, O(n) time instead of O(n²). And the two Python traps: keys must be immutable, and in on a list is O(n) — build a set."
