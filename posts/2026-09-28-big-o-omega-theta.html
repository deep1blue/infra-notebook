Big-O, Ω, Θ: What Complexity Actually Measures

Complexity never measured seconds — it measures operations as a function of input size. Three notations, three derivations, and the read-it-off-the-code skill every later algorithms pattern is stated in.

Algorithms and data structures Lesson

Builds on: nothing on the tree yet — L1 is the trunk. One-line recap of what you already carry: from ML systems you already think in scaling curves (training cost grows with data × epochs, never with how fast your laptop fan spins). Today that instinct gets precise definitions and names.

Intuition: growth, not speed

Complexity never measured seconds. It measures elementary operations as a function of input size n. Why not seconds? Because seconds depend on the machine, the language, the compiler, the day of the week. Operation counts don't. Think of a recipe: "steps per serving" is the algorithm; "how hot your oven runs" is the hardware. Interviewers ask about the recipe.

The reason the question matters at all: at small n, everything looks the same. Two Sum on ten elements — brute force and hash map both finish before you blink. At n = 100,000, one takes milliseconds and the other takes minutes. Big-O is the tool that sees that difference before you run the code. It's the interview version of "will this scale."

The three notations: ceiling, floor, sandwich

Let f(n) be the exact operation count of your algorithm and g(n) a clean benchmark like n or n²:

  • O (big-O) — the ceiling. f(n) = O(g(n)) if f(n) ≤ c·g(n) for all n ≥ n₀. "Never worse than this."
  • Ω (big-Omega) — the floor. f(n) = Ω(g(n)) if f(n) ≥ c·g(n) eventually. "At least this much work, no matter the input."
  • Θ (big-Theta) — the sandwich. Both at once: c₁·g(n) ≤ f(n) ≤ c₂·g(n). The growth rate is pinned, up to constants.

One cultural note: everyone says "Big-O" when they mean Θ. "Merge sort is O(n log n)" — as a pure ceiling that's weak (O(n²) is also true, and useless); the speaker means the tight bound. In an interview, give the tight one even when you call it O.

The math that matters: derive it, don't memorize it

Three derivations cover ninety percent of interview analysis.

1. Counting pairs — brute-force Two Sum. For each i, scan every j > i. Comparisons: (n−1) + (n−2) + … + 1 = n(n−1)/2 = ½n² − ½n. The entire justification for dropping constants: n(n−1)/2 ÷ n² → ½ as n → ∞. The ratio settles to a constant, so the shape is n². Constants and lower-order terms vanish in the limit — that's why we drop them.

2. Halving — where log comes from. While loop: i = n, then n/2, n/4, … until 1. For n = 16: 16 → 8 → 4 → 2 → 1 — four steps, and 4 = log₂16. In general, log₂n iterations: O(log n). The base never matters: logₐn = log₂n / log₂a — a constant factor, and constants die.

3. The recurrence tree — T(n) = 2T(n/2) + O(n). Level 0 does n work; level 1 holds two nodes of n/2 — total n; level 2 holds four of n/4 — total n; … every one of the log₂n levels does n work, so the total is n·log n = Θ(n log n). That's merge sort — and a preview of L16 (divide & conquer).

The code: Two Sum, two ways

def two_sum_bruteforce(nums, target):
    # (n-1) + (n-2) + ... + 1 = n(n-1)/2 comparisons
    # -> Theta(n^2) time, O(1) extra space.
    n = len(nums)
    for i in range(n):
        for j in range(i + 1, n):
            if nums[i] + nums[j] == target:
                return [i, j]

def two_sum_hashmap(nums, target):
    # One pass: for each x ask "have I seen target - x?"
    # Each dict probe O(1) average -> Theta(n) time,
    # Theta(n) space. Time-memory trade: we BUY the
    # linear pass with linear space.
    seen = {}
    for i, x in enumerate(nums):
        need = target - x
        if need in seen:
            return [seen[need], i]
        seen[x] = i

How to spot it: reading complexity off code

  • Single loop over n → O(n). Nested loops both running to n → multiply: O(n²). Triangle inner loop (j from i) → n(n−1)/2 → still O(n²).
  • Counter halved or doubled each step → O(log n).
  • Sequential blocks → add, keep the max.
  • Independent input sizes → name them: O(n·m), never O(n²).
  • Recursion → write the recurrence, draw the tree, multiply levels × work per level.

The Python traps interviewers hide inside loops: sorted() is O(n log n); x in list is O(n) (use a set); slicing copies in O(j−i); list.pop(0) and insert(0, x) are O(n) (use deque); s += c in a loop is O(n²) total (collect in a list, "".join once); max()/sum() over n items is O(n) — calling it per iteration is the classic hidden quadratic.

The 6 pitfalls

  1. Loose O instead of tight Θ — calling a linear scan "O(n²)" is technically true and tells the interviewer nothing.
  2. Hidden O(n) inside loops — slicing, pop(0), string concat, max() per iteration quietly turn O(n) into O(n²).
  3. Average-case amnesia — dict/set are O(1) average, O(n) worst case. Default to worst-case unless you say otherwise.
  4. Log-base pedantry — the base is a constant factor; don't spend interview breath on it.
  5. Forgetting space — the recursion stack counts: naive Fibonacci recursion is O(2ⁿ) time and O(n) space from call depth.
  6. n is the size, not the value — "loop to n" is O(n); "loop over the digits of n" is O(log n).

Connects to: L2 (amortized analysis — that hash-map "O(1)" deserves a closer look at what average-case really means), L4 (constraint decoding: n ≤ 2×10⁵ forces O(n log n), and you can't read constraints without this language), L5–L6 (two pointers and sliding window — the Θ(n) upgrades over today's brute force), L31 (1D DP — every recurrence needs a tight analysis to justify it).

Your thirty-second interview answer "Big-O is a growth-rate claim about operation count, never a stopwatch. I name n, count the dominant work as a function of n, and drop constants and lower-order terms because at scale the fastest-growing term decides everything. O is the ceiling, Ω the floor, Θ the tight bound — and I give the tight one. Two Sum: brute force makes n(n−1)/2 comparisons, Θ(n²); one hash-map pass probes once per element, Θ(n) time for Θ(n) space. That trade is the whole pattern."
